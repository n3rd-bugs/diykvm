DIY PiKVM — API guide for Claude & other agents

A KVM-over-IP appliance: drive the target's keyboard/mouse, watch its screen, manage a virtual USB drive (an EFI System Partition), and talk to a serial console — all over HTTP/WebSocket. LAN-only.

Machine-readable? GET /api returns this whole endpoint list as JSON (public, no auth) — agents can fetch it to discover everything below programmatically.

1. Authentication

Humans log in at /login (session cookie). Agents use the API key. Get it by exchanging credentials once:

curl -sk -X POST https://<pi>:8000/api/login \
     -d username=admin -d password=YOURPASS
# -> {"api_key":"<KEY>"}

TLS is on by default (self-signed cert) — the appliance serves https:// and wss://. The examples below use them; pass curl -k (or rejectUnauthorized:false / an unverified TLS context) to accept the self-signed cert. If you set [web] tls = false, use http:// and ws:// instead.

Then send the key on every request — HTTP header X-API-Key: <KEY> (or Authorization: Bearer <KEY>); for WebSockets add ?token=<KEY> to the URL.

2. Input — keyboard & mouse WS /ws

Connect to wss://<pi>:8000/ws?token=<KEY> and send JSON messages:

MessageEffect
{"t":"kd","code":"KeyA"}key down (code = JS KeyboardEvent.code)
{"t":"ku","code":"KeyA"}key up
{"t":"mm","x":0.5,"y":0.5}absolute move — x,y normalized 0..1 over the target's primary display
{"t":"mr","dx":10,"dy":-4}relative move (trackpad), signed −127..127
{"t":"mb","button":0,"down":true}button 0=left 1=middle 2=right (JS MouseEvent.button)
{"t":"mw","dy":1}wheel (±1)
{"t":"reset"}release all keys & buttons
{"t":"ping","ts":N}latency probe — server replies {"t":"pong","ts":N} echoing your ts, so you can measure round-trip time over this same socket

Latency tool: a live browser↔Pi round-trip meter (using the ping/pong above over /ws) is served at /pingtest — useful to separate network/transport lag from input-device or rendering lag.

Keys: use KeyboardEvent.code values — letters KeyA..KeyZ, digits Digit0..Digit9, Enter Escape Backspace Tab Space, F1..F12, Arrow{Up,Down,Left,Right}, Home End PageUp PageDown Insert Delete, modifiers ControlLeft ShiftLeft AltLeft MetaLeft (and the Right variants), punctuation Minus Equal BracketLeft BracketRight Backslash Semicolon Quote Backquote Comma Period Slash. To type a capital "A": kd ShiftLeft, kd KeyA, ku KeyA, ku ShiftLeft.

Example (Python)

import asyncio, json, ssl, websockets
NOVERIFY = ssl.create_default_context(); NOVERIFY.check_hostname = False; NOVERIFY.verify_mode = ssl.CERT_NONE  # self-signed
async def type_hello(pi, key):
    async with websockets.connect(f"wss://{pi}:8000/ws?token={key}", ssl=NOVERIFY) as ws:
        for c in ["KeyH","KeyI"]:
            await ws.send(json.dumps({"t":"kd","code":c}))
            await ws.send(json.dumps({"t":"ku","code":c}))
        await ws.send(json.dumps({"t":"mm","x":0.5,"y":0.5}))   # cursor to screen center
asyncio.run(type_hello("192.168.1.120","<KEY>"))

3. Screen GET /snapshot GET /stream WS /ws/video GET /api/ocr

GET /snapshotsingle JPEG of the target screen right now
GET /streamlive MJPEG (multipart/x-mixed-replace) of the selected capture card. On slow links prefer /ws/video.
WS /ws/video?token=<KEY>Client-paced video. Per frame the server sends a TEXT message (JSON metadata {ts,kb,level,q,scale}) then the JPEG as a BINARY message, and waits for any reply before sending the next — so it always sends the freshest frame and bounds delay to ~1 frame + RTT (a slow link gets fewer fps, never a backlog). With [video] adaptive=true (default) frames are auto re-encoded smaller when the send→ack cycle exceeds the latency budget. Reply with anything (e.g. an empty frame) to request the next.
GET /api/ocrRead the screen as text. OCRs the current frame (local Tesseract) and returns {image:{w,h}, text, lines[], blocks[]}. Every line has text, a bbox:[x,y,w,h] in image pixels and a conf; lines are in reading order, and blocks group them into layout chunks as they appear on screen (columns/panels stay separate). Query: lang (default eng), psm, min_conf, region=x,y,w,h, scale, words=1 (per-word boxes). On-demand; ~1–4 s per 1080p frame.
import requests
d = requests.get("https://<pi>:8000/api/ocr", headers={"X-API-Key":"<KEY>"},
                 params={"min_conf": 60}, verify=False).json()   # verify=False: self-signed cert
for ln in d["lines"]:                       # text in reading order, with positions
    print(ln["bbox"], round(ln["conf"]), ln["text"])
curl -sk -H "X-API-Key: <KEY>" https://<pi>:8000/snapshot -o screen.jpg

4. Virtual USB drive / EFI boot media /api/msd/*

The target sees a removable USB disk (a GPT disk with a FAT32 EFI System Partition). The drive is either attached to the target or mounted on the Pi for editing — never both.

EndpointDoes
GET /api/msd/status{state, attached, editing, can_edit, image_size}
POST /api/msd/detacheject from target, mount the ESP on the Pi (enables file ops)
POST /api/msd/attachunmount on Pi, hand the disk back to the target
GET /api/msd/ls?path=list a directory (only while editing)
POST /api/msd/upload?path=multipart file=@… upload
GET /api/msd/download?path=download a file
POST /api/msd/mkdir?path= · DELETE /api/msd/rm?path=make / remove
# put a UEFI bootloader on the ESP, then boot the target from it
curl -sk -X POST -H "X-API-Key: <KEY>" https://<pi>:8000/api/msd/detach
curl -sk -H "X-API-Key: <KEY>" -F file=@BOOTX64.EFI \
     "https://<pi>:8000/api/msd/upload?path=EFI/BOOT"
curl -sk -X POST -H "X-API-Key: <KEY>" https://<pi>:8000/api/msd/attach

Scratch block store — bulk host→Pi data /api/store/*

Enable [usb] store_lun to present a second mass-storage LUN: a scratch, read-write block device the target can WRITE(10) to and you read back on the Pi — a generic one-way host→Pi bulk store (logs, captures, firmware dumps …). One-way only; the Pi exposes what the host wrote.

EndpointDoes
GET /api/store/status{present, path, block_size, size_bytes, blocks}
GET /api/store/region?lba=&blocks=read raw blocks the host wrote — blocks×512 B from lba (page-cache, coherent after the host's FUA). Response header X-Store-Blocks = blocks actually returned.

5. Serial console /api/serial/open /api/serial/close WS /ws/serial

Each port has one owner on the server: it is drained continuously and fanned out to any number of WebSocket clients (no "multiple access on port" error). While no client is attached the bytes are held in a bounded backlog; a connecting client receives that backlog once and it is then dropped, and bytes delivered to a live client are never retained — so reconnecting does not duplicate what you already saw. Ports open raw, 8N1, echo off, DTR asserted, with selectable flow control, and stay open after a client leaves (release with /api/serial/close). With [serial] reconnect on (default), a port that drops — e.g. the target re-enumerates its COM port over and over — silently re-opens with backoff, keeping clients attached and the buffer intact, so the churn never reaches the console. Control of the port is yours to drive over this API: by default [serial] autostart is blank, so the Pi does not open the gadget COM port on its own — the other end requests it with POST /api/serial/open when it wants the Pi to attach, and can present a fresh COM port at any time with POST /api/serial/reenumerate. (List a device in [serial] autostart instead if you want the Pi to grab and drain it from boot, socat-style.)

GET /api/serial/portslist serial ports: {ports:[{device,desc,hwid}]}. Includes /dev/ttyGS0 ("USB gadget serial") when the Pi presents a CDC-ACM COM port to the target (set usb.usb_serial).
GET /api/serial/statusopen ports + settings, buffered byte count and client count, plus the supported flow_modes.
POST /api/serial/open{device, baud, flow:none|rtscts|xonxoff, dtr, rts, reconnect, reopen} — open the port and keep it draining into the ring buffer even with no client. Idempotent. This is how the other end requests the Pi attach when autostart is off.
POST /api/serial/close{device} — close the port and stop buffering.
POST /api/serial/clear{device} — discard the port's buffered RX scrollback (the detached backlog replayed to the next client). Returns {discarded, open}; leaves the port open.
POST /api/serial/reenumeratere-enumerate the USB gadget (unbind + re-bind its UDC) so the target re-detects the device and gets a fresh CDC-ACM COM port on demand. Quick bounce (~0.4 s). Because USB enumerates per device, the keyboard, mouse and mass-storage interface also briefly re-appear (~1 s); an open Pi-side port self-heals.
POST /api/gadget/recoverrecover a wedged gadget: unbind + re-bind the UDC while holding the disconnect ~2 s, so a host stuck mid-enumeration (state not attached / addressed-but-not-configured, e.g. after a re-enum storm or a config-change rebuild) fully deregisters and re-enumerates clean — a brief re-enumerate won't unstick it. Bounces all USB ~2 s; returns {recovered, hid_reopened, detail}.
WS /ws/serial?device=/dev/ttyGS0&baud=115200&flow=none&dtr=1&token=<KEY> Binary-clean. Subscribes to the port (auto-opens it with these settings if needed), replays the buffered scrollback, then streams live. RX arrives as WebSocket BINARY frames (raw bytes); transmit BINARY frames (verbatim) or TEXT frames (UTF-8). Status lines arrive as TEXT frames.
import asyncio, ssl, websockets
NOVERIFY = ssl.create_default_context(); NOVERIFY.check_hostname = False; NOVERIFY.verify_mode = ssl.CERT_NONE  # self-signed
async def console(pi, key, dev):
    url=f"wss://{pi}:8000/ws/serial?device={dev}&baud=115200&token={key}"
    async with websockets.connect(url, ssl=NOVERIFY) as ws:
        await ws.send(b"\r")                            # bytes -> written verbatim
        async for msg in ws:
            if isinstance(msg, bytes): handle_serial_bytes(msg)   # raw RX (lossless)
            else: print("[status]", msg)               # text frame = status/info
asyncio.run(console("192.168.1.120","<KEY>","/dev/ttyUSB0"))

6. Events / state stream WS /ws/events GET /api/events/state

Track device state in real time without polling each API. GET /api/events/state returns a full snapshot; WS /ws/events streams it live: on connect it sends one {type:"snapshot",…} with the full state, then one message per change. Every event is a flat JSON object {seq, ts, type, …}. ?replay=N also replays the last N events from just before you connected.

typefields / meaning
snapshotfull state {usb, hid, serial, msd, power, kvmswitch} (sent once, on connect)
usb{udc, bound, state} — the gadget/USB state. state is configured once the target has enumerated the gadget, not attached when the target is gone or has no USB/HID driver (e.g. a dead OS), unbound while re-enumerating. This is how tooling sees the target lose/regain the keyboard, mouse, drive and COM port.
hid{keyboard, mouse, mouse_rel} — whether the Pi currently has each HID device open (i.e. input can reach the target). mouse_rel is false when the optional relative pointer is disabled ([usb] mouse_rel) or shed by the USB endpoint budget; relative input (mr) is then emulated on the absolute mouse.
serial{ports:[{device, open, clients, reconnect, reconnects, reconnecting, error, …}]}; reconnects ticks each time a port self-heals after the target re-enumerated its COM
power{mode, enabled, available, targets:[{label, on, …}]} — the target-power state (as GET /api/power/state); a coarse re-send whenever any target's power changes
msdvirtual-drive state (as GET /api/msd/status: {state, attached, editing, …}); re-sent when the drive attaches / detaches / goes to editing
reenumerate{ok, hid_reopened, detail} — emitted when someone calls POST /api/serial/reenumerate

Alongside those coarse per-domain events, the stream also carries semantic target transitions — each a {seq, ts, type, message, …} object naming the thing that just happened, so tooling can react to an event instead of diffing state: usb.enumerated, usb.enumerating, usb.suspended, usb.resumed, usb.detached; gadget.bound, gadget.unbound; power.on, power.off; serial.enumerated, serial.deenumerated, serial.opened, serial.closed, serial.reconnected, serial.error, serial.error_cleared; hid.online, hid.offline; drive.attached, drive.detached, drive.editing. Fold the coarse events to rebuild state; watch the semantic ones for edges.

Browser — fold the stream into a live state object:

const proto = location.protocol === 'https:' ? 'wss://' : 'ws://';        // match how the page was served
const ws = new WebSocket(`${proto}${location.host}/ws/events?token=${KEY}`);  // browsers may also use the session cookie
const state = {};
ws.onmessage = (e) => {
  const ev = JSON.parse(e.data);
  if (ev.type === "snapshot") Object.assign(state, ev);
  else state[ev.type] = ev;                         // newest event per domain = current state
  if (ev.type === "usb") console.log("target USB:", ev.state);          // configured / not attached / unbound
  if (ev.type === "hid") console.log("HID kbd:", ev.keyboard, "mouse:", ev.mouse);
};

Python — collect state and react (e.g. wait until the target actually has the keyboard):

import asyncio, json, ssl, websockets        # pip install websockets
async def watch(host, key):
    # HTTPS deployment: wss:// + a TLS context (self-signed -> no verify). Plain HTTP: use ws:// and ssl=None.
    ctx = ssl.create_default_context(); ctx.check_hostname = False; ctx.verify_mode = ssl.CERT_NONE
    state = {}
    async with websockets.connect(f"wss://{host}:8000/ws/events?token={key}", ssl=ctx) as ws:
        async for msg in ws:
            ev = json.loads(msg)
            if ev["type"] == "snapshot": state.update(ev)
            else: state[ev["type"]] = ev
            if ev["type"] == "usb":
                print("target USB:", ev["state"], "| HID open:", state.get("hid"))
asyncio.run(watch("192.168.1.120", "<KEY>"))

One-shot snapshot without a socket: curl -sk -H "X-API-Key: <KEY>" https://<pi>:8000/api/events/state.

7. Power, KVM switch & configuration /api/power /api/kvmswitch /api/config

Configure the GPIO targets on the /config page first. Target power — each target's GPIO drives either a latched relay that connects/cuts power, or a momentary front-panel power button ([power] mode):

EndpointDoes
GET /api/power/state{mode:"relay"|"button", enabled, available, targets:[{label, on}]} — on is true (powered), false (cut), or null (not yet driven). In button mode each target also carries {holding, holding_secs, fault} and the top level adds {hold_on_sec, hold_off_sec}.
POST /api/power {"index":0,"on":true}Relay: connect power ("on":false cuts it — a hard power-off). Button: "on":true taps the power button briefly (power on), "on":false holds it for hold_off_sec (force off) — returns immediately while the hold runs; a second request for a target mid-hold gets 409.

External KVM switch — pulse a GPIO to press a hardware switch's select button (display + USB):

GET /api/kvmswitch/state{enabled, available, ports:[{label}]}
POST /api/kvmswitch {"index":0}momentary press of the Nth select button (switch to that target)

Both return 409 if disabled or the index isn't configured.

Read or change settings (i.e. /etc/kvm/kvm.conf) programmatically:

GET /api/config{sections:[{section,title,note,fields:[{key,label,type,value}]}]}
POST /api/configbody {"<section>":{"<key>":"<value>"}} — validated server-side (unknown keys / bad values rejected with 400). Power settings apply immediately; web/video/USB changes need the relevant service restart.
POST /api/config/restart-streamerrestart the video streamer to apply [video] changes
# connect power to the first target, then switch the KVM to it
curl -sk -X POST -H "X-API-Key: <KEY>" -H "Content-Type: application/json" \
     -d '{"index":0,"on":true}' https://<pi>:8000/api/power
curl -sk -X POST -H "X-API-Key: <KEY>" -H "Content-Type: application/json" \
     -d '{"index":0}' https://<pi>:8000/api/kvmswitch

8. Notes

  • The mouse maps to the target's primary display (absolute) — use relative mr for multi-monitor targets.
  • The emulated keyboard is a USB boot keyboard, so it works in the target's BIOS/UEFI setup and boot menus — not just the running OS.
  • GPIO power and KVM-switch control must be wired and enabled on the /config page first; cutting a target's power is a hard power-off (unsaved work is lost).
  • Rotate the API key by re-running setup_auth.py on the Pi.
  • Login is rate-limited per client IP: 5 failed attempts arm an exponential lockout (doubling from 5 s, capped at 300 s) and further attempts get HTTP 429 until it expires. Everything is still LAN-only — don't expose port 8000 to the internet without a VPN.
